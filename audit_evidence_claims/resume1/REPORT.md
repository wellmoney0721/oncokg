# 사람인 지원 문안 독립 검토

## 전체 인상

바이오 실무 경험을 데이터 정규화 문제로 연결한 지원동기는 설득력이 있고, 구체적인 오류 사례에서는 지원자가 무엇을 검토했는지 보입니다.
다만 여러 항목이 ‘기준을 세웠다 → 숫자를 의심했다 → 오류를 고쳤다’로 끝나서, 사람이 겪은 서로 다른 경험보다 하나의 교훈에 맞춰 정리한 글처럼 읽힙니다.
채용자에게는 구현 역량보다 감사 도구와 실패 이력이 먼저 남습니다. 특히 ③의 긴 오류 목록과 ⑤의 사례 재사용을 줄여야 합니다.
제출 전 필수 수정은 88.7%의 적용 시점, 근거 없는 347행, 28%와 58.8%의 모집단, 구조화 검증이 보장하는 범위입니다. 아래 문체 평가는 AI 사용 여부의 판별이 아니라 한국어 채용 문안으로서의 독해 평가입니다.

채용자가 추가로 보고 싶은 것은 다음 세 가지입니다.

- **어디서 결과물을 확인할 수 있는가.** 사람인 경험란에 실제 공개 저장소 또는 동작하는 데모 링크를 넣을 자리가 필요합니다. 공개 URL과 배포 완료는 이 검토에서 확인하지 않았으므로 주소나 서비스 운영 성과를 만들어 넣어서는 안 됩니다. README의 라이브 대시보드 링크 자리도 아직 placeholder입니다.
- **어떤 수준의 Agent/RAG 경험인가.** 현재 근거는 지식그래프 조회와 구조화 주장 검증입니다. 범용 자율 Agent, 벡터 검색, 파인튜닝, 대규모 운영 경험이 입증된 것은 아닙니다. 요구 기술 이름을 더 넣기보다 ‘질문에서 엔티티를 찾고 그래프 근거를 조회한 뒤 검증해 출력한다’는 실제 흐름을 설명하십시오. 평가에서는 현재 파이프라인의 새 홀드아웃이 남아 있음을 밝혀야 합니다.

‘생각보다 많이 나왔습니다’, ‘숫자는 세 번 내려갔지만’, ‘못 고친 결함 14개’가 한 항목에 모이면 정직함보다 실수의 규모가 먼저 보입니다. 한 건의 오류를 어떻게 재현하고 고쳤는지 보여주고, 나머지는 감사 문서 링크로 넘기면 됩니다. 반대로 현재 성능처럼 쓰인 88.7%나 ‘맞는 주장만’ 같은 표현은 반드시 한계를 붙여야 합니다. FACS·gap analysis·BOM&BOE는 관련 실무자에게 의미가 있지만 AI 엔지니어 채용자가 모두 알 것이라고 가정하지 말고, 꼭 필요한 용어만 역할 설명과 함께 남기십시오.
